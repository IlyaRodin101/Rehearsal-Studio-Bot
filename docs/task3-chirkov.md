# Задача 3. Техническое задание для второго разработчика (Chirkov)

## Роль и границы работы

Ветка: `task3/Chirkov`, создаётся от общей ветки `Task-3`.

Исполнитель реализует **только** «горячие» слоты, подписки на базы и уведомления
подписчикам. Правила отмены, платную/бесплатную отмену и уведомление владельцу
реализует Rodin в ветке `task3/Rodin`; эти файлы без необходимости не менять.

Общие изменения модели и БД уже лежат в `Task-3`. Их нельзя дублировать или
переделывать без согласования:

- `Base` содержит `freeCancellationHours` и `penaltyPercent` (по умолчанию 48 и 100).
- В SQLite есть таблица `subscriptions(user_id, base_id)`.
- `BookingRules` содержит методы для проверки срока бесплатной отмены и «горячего» слота.
- `SubscriptionRepository` задаёт контракт хранения подписок.
- `BookingRepository.findByRoom(long roomId)` возвращает брони зала.

## Что нужно реализовать

1. Кнопки главного меню клиента `[Горячие слоты]` и `[Подписка]`.
2. Список «горячих» слотов выбранной базы.
3. Оформление и снятие подписки на конкретные базы.
4. Уведомления подписчикам о новом «горячем» слоте.
5. Сохранение подписок в SQLite и восстановление после перезапуска.

## Термины и правила

- «Горячий» слот — свободное время зала, которое начинается в будущем, но раньше,
  чем истекает срок бесплатной отмены базы:
  `start < now + base.freeCancellationHours()`.
- Слот должен быть доступен для бронирования по общим правилам:
  укладываться в график работы базы, не пересекаться с существующими бронями,
  начинаться не раньше `base.bookingLeadHours()`.
- «Горячие» слоты показываются только по выбранной базе.
- Подписка хранится по паре `(user_id, base_id)`. Повторная подписка идемпотентна.
- Уведомление получают только подписчики той базы, в которой освободилось время.
- Отмена «горячей» брони подчиняется общим правилам отмены, реализованным Rodin.

## Контракты

### SubscriptionRepository

Файл: `src/main/java/ru/urfu/echobot/repository/SubscriptionRepository.java`.

```java
public interface SubscriptionRepository {
    List<Long> findBaseIdsByUser(long userId);
    List<Long> findUserIdsByBase(long baseId);
    boolean isSubscribed(long userId, long baseId);
    void subscribe(long userId, long baseId);
    void unsubscribe(long userId, long baseId);
}
```

Нужна реализация `SqliteSubscriptionRepository` в пакете `repository`.
Таблица уже создана:

```sql
CREATE TABLE IF NOT EXISTS subscriptions (
    user_id INTEGER NOT NULL,
    base_id INTEGER NOT NULL REFERENCES bases(id),
    PRIMARY KEY (user_id, base_id)
);
```

`subscribe` выполняется через `INSERT OR IGNORE`, `unsubscribe` — через `DELETE`.
При удалении базы её подписки удаляются каскадом в `SqliteBaseDeletion`.

### Уведомление о слоте

Рекомендуемый контракт (создать в ветке `task3/Chirkov`):

```java
public interface HotSlotNotifier {
    void notifySubscribers(Base base, Room room, Booking booking, Bot bot);
}
```

Реализация `SubscriptionHotSlotNotifier`:

- получает `subscriptionRepository.findUserIdsByBase(base.id())`;
- отправляет каждому подписчику сообщение:
  `«Горячий» слот: база «Центр», Зал 1, сегодня, 20:00-22:00.`
  с кнопками `[Забронировать]` и `[Пропустить]`;
- ошибка отправки одному пользователю не должна прерывать рассылку остальным;
- не отправляет уведомление владельцу базы как владельцу, если он не подписан.

Точка вызова: после успешного удаления брони в `BookingCancellationService`.
Если ветка `task3/Rodin` ещё не влита, допускается временно добавить вызов
через отдельный интерфейс и заменить заглушку после слияния. Конфликт решается
в пользу сохранения обеих функций: отмена Rodin + уведомление Chirkov.

## Пользовательские сценарии и callback-имена

### Главное меню

Добавить в `BookingMenuController`:

- `[Горячие слоты]` с callback `menu:hot`;
- `[Подписка]` с callback `menu:sub`.

Порядок кнопок: `[Забронировать] [Мои записи] [О базе]`, затем
`[Горячие слоты] [Подписка]`, затем `[Базы]` для владельца.

### «Горячие» слоты

```
Клиент: [Горячие слоты]
Бот:    Выберите базу:
        [Центр] [Север] [Назад]
Клиент: [Центр]
Бот:    «Горячие» слоты базы «Центр»:
        [Зал 1, сегодня, 20:00-22:00]
        [Зал 2, завтра, 10:00-11:00]
        [Назад]
```

Callback-имена:

- `hot:bases` — список баз;
- `hot:base:<baseId>` — слоты выбранной базы;
- `hot:book:<roomId>:<uuuuMMddHHmm>` — начать бронирование слота;
- `hot:skip` — закрыть уведомление или вернуться к списку.

Если слотов нет: `Сейчас «горячих» слотов нет.` и кнопка `[Назад]`.
При выборе слота разрешается начать обычный диалог бронирования с уже выбранными
базой, залом, датой и временем. Если это технически сложно, допускается перевести
клиента на шаг выбора времени с подсвеченным доступным слотом, но нельзя терять
выбранные базу и зал.

### Подписка

```
Клиент: [Подписка]
Бот:    Выберите базы, о «горячих» слотах которых вам писать:
        [✓ Центр] [Север] [Назад]
Клиент: [Север]
Бот:    Подписка на «Север» включена.
        [✓ Центр] [✓ Север] [Назад]
```

Callback-имена:

- `sub:list` — список баз с отметками подписки;
- `sub:toggle:<baseId>` — включить или выключить подписку;
- `sub:back` — возврат в главное меню.

Тексты:

- включение: `Подписка на «Север» включена.`;
- отключение: `Подписка на «Север» отключена.`;
- после действия снова показывается список с актуальными отметками.

## Предлагаемая структура классов

Каждый класс — не больше 200 строк. Рекомендуется:

- `HotSlotService` — вычисление свободных «горячих» слотов;
- `HotSlotController` — диалог списка слотов;
- `SubscriptionService` — включение и отключение подписок;
- `SubscriptionController` — диалог подписки;
- `SubscriptionHotSlotNotifier` — рассылка уведомлений;
- `SqliteSubscriptionRepository` — хранение подписок.

Не создавать классы «на всё»: расчёт слотов, сообщения и хранение разделить.

## Тесты

Обязательные модульные тесты:

1. Свободный слот раньше срока бесплатной отмены попадает в «горячие».
2. Слот позже срока бесплатной отмены не попадает в «горячие».
3. Занятый слот и слот вне графика не попадают в «горячие».
4. Подписка сохраняется в SQLite, повторная подписка не создаёт дубль.
5. Отписка удаляет подписку.
6. Уведомление получает только подписчик нужной базы.
7. После отмены брони подписчики базы получают уведомление о слоте.
8. Два одновременных клиента могут независимо подписаться и получить уведомления.
9. После перезапуска репозитория подписки сохраняются.

Тесты должны использовать `DummyBot`; для каждого одновременного клиента —
отдельный экземпляр бота.

## Регламент

- Java 25, Maven, без Lombok.
- JavaDoc у классов, полей и методов.
- `static` только для `String` и примитивных констант.
- Константы: `ИМЕНУЮТСЯ_ВОТ_ТАК`.
- CamelCase для классов, методов и переменных.
- Каждый класс не больше 200 строк.
- `mvn test` и `mvn checkstyle:check` должны проходить без нарушений.

## Критерии приёмки

- В главном меню клиента есть `[Горячие слоты]` и `[Подписка]`.
- «Горячие» слоты считаются по правилам базы и не показывают занятое время.
- Подписка включается и отключается кнопками, сохраняется в БД.
- Подписчики получают уведомления только о слотах выбранных баз.
- После отмены брони освободившийся «горячий» слот рассылается подписчикам.
- Все новые классы не больше 200 строк, тесты и checkstyle проходят.
